# Что исправлено (ревью кода + подготовка к Railway)

## Запуск на Railway
- **`DATABASE_URL` от Railway (`postgresql://…`) ронял бота** — SQLAlchemy выбирал синхронный
  драйвер. Теперь `postgresql://` / `postgres://` автоматически приводятся к `postgresql+asyncpg://`,
  а `sslmode=` переводится в `ssl=` для asyncpg.
- Бот ждёт базу до ~60 с при старте (Postgres / приватная сеть Railway могут подняться позже), а не
  падает и не тратит лимит перезапусков. Повторяет и первый запрос к Telegram при сетевой ошибке.
- `railway.json`: сборка из Dockerfile, команда запуска, перезапуск при сбое.
- Dockerfile: зависимости ставятся из закреплённого `requirements.txt` (воспроизводимая сборка),
  без компилятора, процесс работает не от root; добавлен `.dockerignore` (раньше `.env` с токеном
  попадал в образ). Добавлен `tzdata`.
- `pyproject.toml`: добавлены build-system и список пакетов — `pip install -e ".[dev]"` раньше падал.
- Корректное завершение по SIGTERM (редеплой): незаконченные обработчики получают до 8 с,
  планировщик останавливается, соединения с БД закрываются.
- Сообщения, пришедшие во время перезапуска, больше не выбрасываются (`drop_pending_updates=False`).
- `alembic/env.py`: миграции из приложения больше не сбрасывают настройки логирования (пропадали
  логи aiogram), а пароль с `%` в URL больше не ломает Alembic.
- Валидация настроек при старте: неверный `TIMEZONE` / пустой `BOT_TOKEN` дают понятную ошибку.

## Ошибки бизнес-логики
- **Отменённую запись можно было «воскресить»**: старая кнопка «Подтвердить» у мастера, «Перенести»
  у клиента или смена статуса админом возвращали отменённую запись в работу (иногда поверх чужой
  записи). Теперь везде проверяется статус; восстановление проверяет, свободно ли время.
- **Двойное бронирование при одновременных запросах**: `SELECT … FOR UPDATE` по пересекающимся
  строкам не мешал двум транзакциям вставить пересекающиеся интервалы. Теперь блокируется строка
  мастера; вставка идёт в SAVEPOINT (раньше `rollback()` всей сессии ломал дальнейшую обработку).
- **Время из кнопки не проверялось**: подделанный callback позволял записаться на 03:00 или на
  занятое/прошедшее время. Теперь время сверяется с расписанием и при выборе, и перед созданием.
- Можно было записаться к мастеру на услугу, которую он не оказывает (кнопка «Выбрать мастера»
  из общего списка мастеров).
- Перенос клиентом сразу ставил статус «подтверждена» без мастера и игнорировал `MIN_CANCEL_HOURS`.
  Теперь новое время снова уходит мастеру с кнопками «Подтвердить/Отклонить», а поздний перенос
  запрещён так же, как поздняя отмена.
- Старые кнопки «Подтвердить/Отклонить» у мастера после переноса записи применялись к новому
  времени, которого мастер не видел. Теперь в кнопке зашито время записи, устаревшая кнопка
  отвечает «время уже изменилось».
- Гонка «мастер подтверждает ↔ клиент отменяет» могла вернуть отменённую запись: статус теперь
  проверяется по строке, заблокированной в транзакции (`SELECT … FOR UPDATE`).
- После смены мастера у неподтверждённой записи новый мастер получает уведомление с кнопками.
- Смена мастера админом уведомляла и показывала **старого** мастера; теперь — нового, а старый
  мастер получает уведомление, что запись у него снята.
- Удержание слота защищало только точное время начала: второй клиент мог «держать» пересекающийся
  слот. Удержание снимается при отмене/изменении записи.
- Особые часы (`custom_hours`) не могли открыть обычно нерабочий день.
- Мастер видел длительность вместе с буфером.

## Telegram-диалоги
- **HTML-разметка ломала отправку**: клиент с `<` или `&` в имени или комментарии не мог дойти до
  подтверждения записи (ошибка на шаге сводки), уведомление мастеру с таким текстом молча не
  доставлялось, а подтверждение записи мастером откатывалось. Тексты отправляются без разметки.
- **Кнопки главного меню «съедались» как ввод**: нажатие «Мои записи» / «Админ-панель» на шаге ввода
  телефона, комментария, причины отмены, отзыва или рассылки сохранялось как текст. Теперь кнопка
  меню завершает незаконченный шаг (иначе любое сообщение через несколько дней отменило бы запись).
- Телефон, введённый вручную, не проверялся (любой текст, ошибка БД при длине > 32).
- Двойное нажатие кнопки обрабатывалось дважды (например, рассылка уходила всем дважды): апдейты
  одного пользователя теперь обрабатываются последовательно.
- После рестарта (FSM в памяти) старые кнопки крутили «часики» бесконечно — теперь бот отвечает
  «кнопка устарела», а непонятный текст возвращает в главное меню.
- Рассылка отвечала на callback только после отправки всем (Telegram уже считал запрос
  просроченным, админ видел ошибку) — теперь идёт в фоне с отчётом по завершении.
- Ошибка отправки уведомления (сеть, лимиты Telegram) откатывала уже созданную запись; теперь запись
  сохраняется до уведомлений, а уведомления никогда не прерывают сценарий.
- Длинные списки (клиенты, отзывы) могли превысить лимит 4096 символов — делятся на части.
- После ввода телефона возвращается главное меню (раньше оставалась только кнопка «Поделиться»).
- Даты для ro/en-пользователей выводились с русскими названиями месяцев.

## Безопасность
- Админ, удалённый из `ADMIN_IDS`, сохранял права навсегда (роль оставалась в БД). Теперь
  `ADMIN_IDS` — источник истины (роль `owner` в БД — для постоянных админов).
- Экспорт CSV защищён от формульных инъекций (`=`, `+`, `-`, `@` в именах).
- Телефоны и тексты SMS больше не пишутся в логи.
- Шаги админ-редактирования и рассылки проверяют права на каждом шаге; код языка из кнопки
  проверяется.

## Напоминания и фоновые задачи
- Настройки `REMINDER_HOURS_BEFORE` / `_2` игнорировались (часы были зашиты в код).
- «Напоминание» приходило сразу после записи, если запись сделана внутри окна напоминания.
- После переноса записи напоминание не приходило (ключ не учитывал время начала); перенос внутрь
  окна не вызывает мгновенного «напоминания»; если подходят оба окна сразу — приходит одно.
  Отметки, сделанные прежней версией бота, учитываются (без повторов при обновлении).
- Ошибка в одной задаче планировщика откатывала отметки уже отправленных напоминаний (повторная
  отправка) и блокировала остальные задачи.

## Демо-данные
- `SEED_DEMO=false` отключает демо-данные (раньше они всегда писались в рабочую базу).
- Демо не создаётся повторно, если в базе уже есть услуги.
- Название/адрес/телефон салона в демо берутся из `SALON_NAME` / `SALON_ADDRESS` / `SALON_PHONE`
  (раньше было жёстко «Салон «Пример»», и переменные окружения игнорировались).
- `MASTER_TELEGRAM_ID` (был описан в README, но не работал) привязывает первого демо-мастера к
  реальному аккаунту — в том числе если переменную добавили после первого запуска.
- Изменённые позже `SALON_NAME` / `SALON_ADDRESS` / `SALON_PHONE` / `TIMEZONE` / `CURRENCY`
  применяются к сохранённым настройкам салона при следующем запуске.
